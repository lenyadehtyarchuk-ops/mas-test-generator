# MAS Test Generator

Курсовой проект: многоагентная система генерации и проверки модульных тестов
по исходному коду и естественно-языковому описанию функции.

Поддерживаются Python (pytest) и Java 17 (JUnit Jupiter 5). Оркестратор — обычный
конечный автомат; LLM используется только тремя агентами. Интерфейс — REST API
и Swagger, без отдельного веб-приложения.

## Быстрый запуск на Windows

Нужен Docker Desktop с работающим Linux Engine и Docker Compose v2.
Python на хосте нужен только для клиентских скриптов и локальных тестов.

1. В существующем проекте сохраните свой `.env`. Для новой копии создайте его:
   `Copy-Item .env.example .env`.
2. Укажите в `.env` адрес API, ключ и точное имя модели вашего провайдера.
   Шаблон содержит пример, а не рабочий ключ.
3. Выполните из корня:

~~~powershell
.\scripts\start.ps1
~~~

Либо напрямую:

~~~powershell
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
~~~

API: http://127.0.0.1:8000/docs

При первом запуске скачиваются базовые образы, Python-зависимости и JUnit jar.
Это требует доступа к Docker Hub, PyPI и Maven Central. При выполнении тестов
ничего из интернета не устанавливается. Только порт оркестратора доступен с хоста,
и он привязан к localhost.

## Настройка LLM

| Переменная | Назначение |
| --- | --- |
| LLM_API_KEY | Ключ OpenAI-совместимого провайдера |
| LLM_BASE_URL | Базовый адрес API с /v1 либо адресом, указанным провайдером |
| LLM_MODEL | Точное имя доступной модели |
| LLM_OUTPUT_MODE | auto, json или prompt |
| LLM_TIMEOUT | Таймаут одного обращения к LLM, секунды |
| AGENT_HTTP_TIMEOUT | Таймаут обращения оркестратора к агенту |
| RUNNER_EXECUTION_TIMEOUT | Общий бюджет компиляции и выполнения, 1–30 секунд |

Режим `auto` сначала использует Structured Outputs. При явном отказе провайдера
от `json_schema` переключается на JSON mode. Ошибки ключа, отказ модели,
повреждённый JSON и ошибки сервера не маскируются повторной генерацией.
Если провайдер не поддерживает даже JSON mode, выберите `prompt`:
схема передаётся в системном сообщении, а ответ проверяется Pydantic.

Пример локальной Ollama: `LLM_BASE_URL=http://host.docker.internal:11434/v1`,
`LLM_API_KEY=ollama`, имя установленной модели в `LLM_MODEL`. У сервиса Ollama
должен быть доступный контейнерам адрес. Совместимость конкретной модели и её
качество нужно проверить отдельно.

После изменения `.env` пересоздайте сервисы: `docker compose up -d`.
Healthcheck агентов проверяет работоспособность HTTP-сервиса; он не тратит токены
и не проверяет ключ у провайдера. Первый запрос может обнаружить ошибку ключа или модели.

## Отправка задачи

~~~powershell
python scripts/submit_task.py examples/python_pass.json --output outputs/python_pass.json
python scripts/submit_task.py examples/python_bug.json --output outputs/python_bug.json
python scripts/submit_task.py examples/java_pass.json --output outputs/java_pass.json
python scripts/submit_task.py examples/java_bug.json --output outputs/java_bug.json
~~~

Эти запросы обращаются к настроенному LLM-провайдеру и могут расходовать его квоту.

Прямой запрос `POST /api/v1/task`:

~~~json
{
  "language": "python",
  "source_code": "def add(a, b):\n    return a + b\n",
  "nl_description": "Функция add возвращает сумму двух целых чисел.",
  "max_iterations": 3
}
~~~

Python-код сохраняется как `solution.py`; тесты импортируют функции из `solution`.
Java-код — один `public class Solution` без `package`; тесты — `SolutionTest`.
Внешние зависимости пользовательского кода не устанавливаются.
Лимит итераций — от 1 до 5. HTTP-запрос синхронный: ответ возвращается после
завершения всей задачи. `task_id` используется для трассировки, задачи в БД не хранятся.

## Как работает цикл

1. Аналитик один раз извлекает требования и сценарии из ТЗ. ТЗ имеет приоритет над
   текущим поведением программы; незаданные требования придумывать нельзя.
2. Генератор создаёт полный файл тестов.
3. Соответствующий раннер выполняет тесты во временной папке.
4. При синтаксической ошибке теста, ошибке импорта или таймауте обратная связь
   направляется генератору без вызова отладчика. Таймаут сам по себе не доказывает
   ошибку теста: он может возникнуть в исходном коде.
5. При FAILED отладчик различает TEST_FAULT и CODE_BUG. Ошибка теста возвращается
   генератору, а предложенное исправление исходника запускается с теми же тестами.
6. История содержит код тестов, результат исполнения и вердикт для каждой итерации.
   Проверка исправления хранится отдельно в `fix_execution_result`;
   `last_execution_result` сохраняет результат последней генерационной итерации.

| final_status | Значение |
| --- | --- |
| ALL_TESTS_PASSED | Есть хотя бы один прошедший тест, падений нет |
| BUG_DETECTED_AND_FIXED | Баг определён отладчиком, исправление прошло повторный запуск |
| BUG_DETECTED_FIX_FAILED | Баг определён, предложенное исправление не прошло тесты |
| MAX_ITERATIONS_EXCEEDED | Лимит обратной связи исчерпан |
| SOURCE_ERROR | Исходный файл не проходит синтаксический анализ или компиляцию |

Два дополнительных статуса предотвращают ложное сообщение об исправлении и
бесполезное переписывание тестов при ошибке синтаксиса исходника.
HTTP 422 означает неверный входной JSON; 502 — недоступный сервис/неверный контракт;
504 — таймаут межсервисного обращения. При ошибках инфраструктуры частичный
`TaskFinalResponse` не возвращается.

## Сервисы

| Сервис | Порт внутри Compose | Метод |
| --- | --- | --- |
| orchestrator | 8000 | POST /api/v1/task |
| agent-analyst | 8001 | POST /analyze |
| agent-generator | 8002 | POST /generate |
| agent-debugger | 8003 | POST /triage |
| runner-python | 8004 | POST /execute |
| runner-java | 8005 | POST /execute |

У каждого сервиса есть GET /health. Оркестратор и агенты подключены к
`mas-internal-net`. Оркестратор и раннеры — к `sandbox-isolated-net` с
`internal: true`. Раннерам не передаются LLM-ключи и переменные HTTP-прокси.
Временные файлы размещаются в tmpfs, корневая ФС read-only, процессы работают
без root. Ограничены CPU, память, число процессов, размер вывода и время.
На POSIX по завершении уничтожается группа процессов. Каждый раннер допускает
одну задачу одновременно, при занятости возвращает 503; оркестратор передаёт 502.
Очередь, многопользовательская авторизация и постоянное хранение задач не реализованы.

Это учебная контейнерная песочница. Пользовательский код и HTTP-процесс раннера
работают внутри одного контейнера под одним UID. Такая схема не рассчитана на
враждебный код: он может влиять на отчёты и состояние своего контейнера.
Для публичного сервиса нужны одноразовые контейнеры/VM на задачу, отдельные UID,
дополнительный контроль сети и аутентификация. Локальные тесты раннеров запускают
только заранее известные примеры; произвольный код на хосте запускать не следует.

Успешный повторный запуск подтверждает исправление относительно текущего набора
тестов. Полнота тестов и семантический вердикт LLM не гарантируют отсутствие других багов.

## Проверки

Установка и полный набор локальных тестов:

~~~powershell
.\scripts\test.ps1
~~~

Либо:

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
~~~

Локальные тесты проверяют контракты, LLM-fallback на подменённом клиенте,
ветвления оркестратора, XML-отчёты, процессы, таймаут и ограничение вывода.
Сетевые вызовы оркестратора подменяются: токены не расходуются.
Проверки FastAPI, реального pytest и Java при отсутствии зависимостей явно
пропускаются. Для Java-тестов на хосте нужны JDK 17 и переменная `JUNIT_JAR`
с абсолютным путём к standalone jar версии 1.11.4.

Проверка настоящих контейнерных раннеров после запуска системы:

~~~powershell
python scripts/smoke.py
~~~

Скрипт проверяет проходящие и падающие тесты Python/Java, ошибки компиляции,
пустой набор, таймаут и отсутствие внешнего TCP-доступа из раннеров. LLM не вызывается.
Для проверки полного процесса с настоящим LLM выполните четыре запроса из раздела
«Отправка задачи» и изучите ответы: вывод модели может различаться между запусками.

Фактически выполненные при подготовке проверки перечислены в `VERIFICATION.md`.

## Диагностика

~~~powershell
docker compose logs --tail 100
docker compose logs -f orchestrator agent-analyst agent-generator agent-debugger
docker compose ps
docker compose down
~~~

Если Docker сообщает об отсутствии `dockerDesktopLinuxEngine`, запустите Docker Desktop
и дождитесь состояния работающего Linux Engine. Если сборка не может скачать зависимости,
проверьте доступ Docker к реестрам. Если запрос возвращает 502, проверьте LLM-параметры
и логи соответствующего агента. Ключи не выводятся в HTTP-ответах приложения;
не публикуйте вывод `docker compose config`, так как он может содержать подставленный ключ.

## Перенос подготовленной версии в исходный проект

Если вы получили эту версию архивом, распакуйте его отдельно и из распакованной
папки выполните:

~~~powershell
.\scripts\install_to_original.ps1
~~~

По умолчанию целевая папка — `D:\май проджектс\mas-test-generator`.
Скрипт копирует только файлы из `delivery-manifest.json`, сохраняет `.env` и `.git`,
а перед заменой копирует прежние версии в `.mas-backups\<дата-время>`.
Никакие существующие файлы не удаляются. Другой путь задаётся параметром
`-Destination 'полный путь к mas-test-generator'`.

Подготовленная рабочая копия сохраняет исходную историю Git. Коммиты и push
автоматически не выполняются.
